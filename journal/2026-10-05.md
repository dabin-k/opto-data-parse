# 2026-10-05

This codebase generates population_rates npz file. The reported activity contains averaged activity over multiple repeats.
However, I want to remove the averaging logic from this database.
The averaging, if desired, should be prescribed in downstream processes and the job of this codebase instead should be to output single trial data. 

Currently, data_loader outputs a numpy array of shape (n_cond, n_folds, 2, n_bins). 
In theory, we want something like (n_cond, n_repeats, 2, n_bins) where n_repeats is the actual number of repeats found for each experiment condition. 
However, n_repeats differ for different conditions.

- **Todo 1 (design) — agreed with Dabin.** Per-session *flat trial table*
  instead of a padded `(n_cond, n_repeats, 2, n_bins)` cube:
  - `counts` uint16 `(n_trials, 2, n_bins)` — raw per-trial spike counts, all exp types together.
  - Per-trial columns `(n_trials,)`: `cond_idx`, `exp_num`, `trial_in_exp`, `onset_sample`.
  - Condition table: per-condition columns `exp_type`, `pulse_type`, `ipi_ms`, `dur1_ms`,
    `dur2_ms`, `first_pop`, `second_pop` (plain arrays, replaces the JSON string).
  - Scalars: `time_axis`, `bin_samples`, `sampling_freq_hz`, `animal_id`, `session`, `ei_cache_key`.
  - One file per (mouse, session), same schema everywhere.
  - Why not padding: trials/condition range 10–308 (M151020: median 10, max 184), so a
    NaN-padded cube is mostly NaN and every reduction must remember `nan*`.
  - Why counts, not normalised rates: the paper normalises the *trial-averaged* PSTH;
    per-trial baseline normalisation divides by single-trial baselines that can be ~0, and
    mean-of-ratios ≠ ratio-of-means. Smoothing/normalising/folding all move downstream.
  - Open: trials whose window is clipped at an experiment boundary currently get silent
    zeros (`win_start = max(..., exp_start)`); harmless when averaged, misleading per trial.
    Decision: one fixed (pre_s, post_s) window, set in `regenerate_population_rates.py`.
    Trials that don't fit it are excluded (count logged, not zero-filled); todo 7 gives the
    user tools to pick a window that loses few trials.
  - "Table" = parallel NumPy arrays sharing axis 0 (struct-of-arrays), returned as a plain
    `dict[str, np.ndarray]` whose keys are the npz keys — no dataclass/pandas for now.
  - API: add a new, modular `get_trial_counts` (+ small helpers) rather than reshaping
    `get_population_responses`. Fate of old consumers (figures, plot script, EDGAR files)

- **Trial-label audit** (Dabin asked why exp 2 has single_E trials). Tools: scratchpad
  `ttl_audit.py` and `tp_check.py`, reading raw ain131/132 TTLs, about 30 s per experiment.
  - *Experiment numbers* = mpep run order within series 1 (`1/<exp>/`,
    `<animal>_1_<exp>.ns5`). The manifest `ns5files2unify` / `SELECTED_EXPERIMENTS` give the
    concatenation order and start times.
  - *exp 2 single_E is real*: `stim2PulsesRandNoise` has 96 conditions, including intT = 0
    singles. The TTLs agree: 1 pulse on the right channel, ~1 ms wide.
  - **Finding 1 — visual-noise confound (Protocol, certain).** RandNoise protocols carry
    `c` (contrast 0/100), `Tp` (laser time within the stimulus, 400–1300 ms), `Vamp`
    (0 = no laser) and `seedw`. The loader keys conditions on (pulseType, intT, dur) only,
    so laser trials *during visual noise* (c = 100) are pooled with c = 0 trials. That is
    42 % of laser trials in M150605 / M150609_1 / M150609_2, 20 % in M150823, 6 % in M151020.
  - **Finding 2 — IPI-1000 trials aligned to pulse 2 (TTL, certain; seen in M150605 exp 2).**
    Pairs are 1001.5 ms onset-to-onset, above `iti_gap_s = 1.0`, so the pair is split. The
    first pulse is left unmatched (20 groups) and the Timeline trial matches the *second*
    pulse. Likely in every mouse with intT = 1000 (M150605, M150609 ×2); legacy files too.
  - **Finding 3 — `intT` = gap from end of pulse 1 to start of pulse 2 (TTL).**
    Onset-to-onset = intT + dur1 (+1.0 ms with 1 ms pulses in M150605; +2.0 ms with 2 ms
    pulses in M151020 exp 14), plus ~0.05 % clock drift. The paper's IPI definition is not checked.
  - Why the matcher was fooled: it pairs the laser onset with the nearest Timeline StimStart
    within 1 s, but the laser fires `Tp` after StimStart. onset − StimStart spreads −66 to
    +820 ms; onset − (StimStart + Tp) is constant to ±65 ms (exp 2).
  - Gaps are bimodal in exp 2: within a trial ≤ 1.0015 s, between trials ≥ 2.034 s. A 1.5 s
    split gives 460 TTL trials == 460 Timeline trials with Vamp > 0.
  - Proposed source of truth (not implemented, awaiting Dabin):
    - TTL = when/which laser fired.
    - Timeline order + Protocol = full label (incl. c, Tp, Vamp, seedw).
    - Match on StimStart + Tp.
    - Cross-check pulse count / channel order / interval per trial.
